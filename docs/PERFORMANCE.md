# 项目列表加载：原因与验证边界

本文记录本轮代码层诊断与合成测量，不是对生产账号、真实 DSH GUI 或公网延迟的测量。基线源码为0.10.0（提交 `0fa991e`）。未登录真实云端账号、上传真实数据或部署服务器。

## 原因

1. **串行网络请求。** 原 Host 先查询健康接口，再读 v2 项目页，最后读取整个 v1 项目列表；尚无 serverId 的身份还需要 capabilities。常规已有身份为3次请求，首次身份发现为4次，翻页另计。所有列表都完成后才返回。
2. **重复处理历史与清单。** 原 v1 列表每次遍历全部历史检查点构造项目摘要，再解析每个项目的最新清单；v2 列表每个项目重复读取 head，并为名称、文件数和冲突数解析／规范化整份最新清单。完整历史 blob 验证是在存储打开时，不是每次列表请求都读取全部 blob。
3. **Host 身份检查夹带旧功能扫描。** 原双向准入反复使用完整旧 status：枚举并校验所有工作区目录，解析所有保留的旧队列，还核对旧恢复台账。这些清单不是当前账号身份的证据，却在每次列表响应／准入回调中付出开销。
4. **过早加载列表。** 原配对弹窗一打开就加载云端，即使用户只是准备选择本地工作区。新交互只在明确进入云端选择器时查询，短时缓存也不代表新的写入授权。

## 改法与安全边界

- 新增只读 `/v2/project-catalog`，在同一分页快照中返回 v1/v2 项目摘要；正常单页发现只需 capabilities + catalog 两次请求。服务端声明 `projectCatalog:true` 才使用新接口；0.9.0起的旧协议2服务器继续走兼容接口，不假装拥有新能力。
- 旧历史汇总仅在不可变检查点数组换代时重建，暖态分页不再遍历所有历史；认证续期等未改变历史的写入不触发重建。
- v2 摘要只保留已在打开／提交时验证过的名称及计数。**每次所选项目仍读取当前 head、record、manifest，并核对当前字节的摘要**；不是信任 mtime、TTL 或跳过完整性保护。v1 最新摘要也绑定当前 hash 校验过的字节。
- 分页游标绑定服务进程和目录代次；提交／重启使代次失效。代次变化会丢弃整组已收集页面并有限重试，不把不同代次拼在一起。达到分页上限明确标记 partial。
- 损坏的 v2 项目也会遮蔽同名 v1 项目；不能以历史旧快照冒充可同步的最新内容。旧服务端的兼容合并同样保守处理损坏与截断目录。
- `accountStatus()`只读取当前原生授权、重新认证状态、身份、revision 和忙碌状态，不缓存凭据，不扫描旧队列或工作区；旧内部 status 的兼容语义保留。每次远端响应后的账号／epoch 检查仍执行。
- 云端列表短时缓存只供同身份、同 revision 的显示与选择；计划和提交仍由 Host 复核最新账号、目录、head 和授权。手动刷新可以主动重新查询，身份／revision 变化会使旧选择失去权限。

## 合成测量

以下均为 Windows 本机 loopback／临时合成目录。时间随机器、缓存、负载而变化；测试断言主要依赖请求、读取、解析和迭代次数，不以毫秒阈值保证公网性能。

### 项目目录

夹具：3个 v2 项目，每个512个文件条目；4个 v1 项目，每个12次修订、128个文件条目。

| 指标 | 0.10.0首次身份发现基线 | 新目录冷态／暖态 |
| --- | ---: | ---: |
| HTTP请求 | 4（已有身份通常为3） | 2 |
| head读取 | 6 | 3 |
| 当前record读取 | 3 | 3 |
| 当前v2／v1清单读取 | 3／4 | 3／4 |
| 完整v2清单解析 | 3 | 0 |
| 完整v1清单解析 | 4 | 冷态4／暖态0 |
| blob读取 | 0 | 0 |
| 观测耗时（基线一次／最终全量一次） | 178.22ms | 冷态75.14ms／暖态57.39ms |

其他优化后运行的观测约54–123ms，因此上表不是速度承诺。兼容旧端点也受益于服务端摘要改进；最终全量中的一次暖态观测为81.57ms，但请求数仍为4。

若仅作**模型计算**，假设每次 RTT 为80ms，不考虑磁盘及并发，则4／3次串行请求的网络预算320／240ms可降至160ms；这不是测得的公网 RTT。

### 历史聚合

夹具：20,000条历史记录、20个项目，连续读取10次。以下时间为最终全量运行中的观测，其他定向运行会有波动。

- 复现旧聚合：实际访问200,000条记录，209.79ms。
- 新索引首次构建：访问20,000条记录，16.32ms。
- 暖态10次读取：访问0条历史记录，1.25ms。
- 新提交将代次替换后：重新访问20,001条，不能沿用旧索引。
- 2条项目分页只读取所选2个项目的最新清单，而非整个库存。

### Host账号准入

夹具：40个已登记工作区、8份保留队列清单，每份128个文件条目。

| 单次状态读取 | 工作区清单枚举 | 旧队列解析 | 最终全量中的一次观测 |
| --- | ---: | ---: | ---: |
| 原完整 status | 1次 | 1轮（8份清单） | 225.02ms |
| 轻量 accountStatus | 0 | 0 | 60.77ms |

此测量比较同一当前账号的读取投影；已验证过期、撤销、损坏身份、revision 竞争、忙碌状态与秘密剔除仍正确。不会因为旧队列损坏而把它当作有效身份，也不会把旧队列自动发送出去。

回归入口：[目录性能与完整性](<../tests/cloud-discovery-performance.test.mjs>)、[轻量账号状态](<../tests/account-status-performance.test.mjs>)。最终整套结果见[测试记录](<TESTING.md>)，不将这些定向测试相加当作全量计数。

## 哪些需要升级、哪些尚未验证

- 新选择器、延迟加载和轻量 Host 读取随插件升级生效；服务器0.9.0起仍可按兼容协议工作。
- **统一目录与服务端索引优化必须另行升级服务端才生效。** 构建插件或推送源码不会自动部署服务器；本轮没有进行生产升级。
- 未测量真实云端磁盘、TLS／DNS／网络延迟、实际用户项目分布或真实 GUI 渲染。若上线后仍慢，应在明确授权的只读诊断中分开记录浏览器到 Host、Host 本地准入、远端各请求、分页和渲染耗时，不能用此处 loopback 数据替代。
